# 高校教务 RAG 召回优化报告

**周期**：召回侧三级优化（多路召回 → Query 改写 → Rerank）+ 文档级去重 + Embedding 选型
**代码库**：`academic-affairs-qa` @ master
**评估数据**：`docs/eval_results/`（每级一个子目录，含 `result.json` + `report.md`）

---

## 一、结论先行

| # | 结论 | 数据支撑 |
|---|---|---|
| 1 | BM25 多路召回**扩池有效、排序不足** | Top5 +3.29pp（捞回正确文档），Top1 -3.30pp（排不上去） |
| 2 | Query 改写**净效果为负，不启用** | 5 组消融，提升:退步 ≈ 1:2，85% 题目无影响 |
| 3 | Rerank 是**表格子集的有效补偿手段** | 表格 Top1 +13.04pp，表格 Top3 → 95.65% |
| 4 | 文档级去重**释放被重复文档占据的槽位** | Top3 +4.39pp、Top5 +4.39pp、表格 Top3 → 100% |
| 5 | bge-large-zh-v1.5 **优于** bge-m3 | Top1 +9.9pp、Top3 +6.6pp、延迟低 2 倍 |
| 6 | 端到端 Top3 92.31% → **96.70%**（+4.39pp） | 五级对比表 |

**最重要的方法论收获**：召回优化不是"每级都要涨"，而是**每级解决一个明确的问题**。BM25 解决"正确文档进不了候选池"，Rerank 解决"进了候选池排不到前面"，去重解决"同一文档占满槽位导致其他文档进不来"，改写试图解决"用户口语和文档术语不匹配"——但实测发现本项目 base retriever 已足够好，改写引入的噪声大于收益，于是**主动止损下线**。

## 三、逐级增量归因

### 3.1 第 1 级：基线（纯向量）

**配置**：`bge-large-zh-v1.5`（1024 维）+ Milvus 余弦距离，top_k=10

**指标**：Top1 74.73% / Top3 92.31% / Top5 94.51%；表格 86.96% / 95.65% / 95.65%

**Top-3 未命中 7 条，根因高度集中**：

| 根因类型 | 题目 | 现象 |
|---|---|---|
| 同族文档语义不可分 | Q13 | 问"计算机科学与技术专业"，Top-3 全是网络工程/软件工程/数字媒体培养计划 |
| 近义文档压制 | Q19、Q58 | 问"创新分申请补充说明"（本学期），召回"创新学分认定办法"（长效制度） |
| 近义文档压制 | Q32、Q70 | 问"英语免修申请操作"，召回"英语课程免修重考办法" |
| 近义文档压制 | Q80 | 问"勤工助学报名截止"，召回通用"勤工助学.docx" |
| 主体错位 | Q67 | 问"信息素养大赛谁办的"，召回"命题范围"而非"举办通知" |

**关键洞察**：7 条里有 6 条不是"语义理解错了"，而是**"两个文档语义太像，向量分不开"**。这直接指向 BM25——因为区分它们的恰恰是**低频专名 token**（"计算机科学与技术" vs "网络工程"、"补充说明" vs "认定办法"、"举办通知" vs "命题范围"）。

### 3.2 第 2 级：+多路召回（BM25）

**实现**：
- `src/retrieval/bm25_retriever.py`：`rank_bm25` + `jieba` 分词，预置 13 个教务术语自定义词典
- `src/retrieval/fusion.py`：RRF + Weighted 两种融合策略，`rrf_fuse` 支持 `weights` 参数
- `export_chunks_from_milvus.py`：从 Milvus 反查导出 `chunks.json`（541 条），**避免重跑 Embedding API**
- `ScoredVectorRetriever`：调 `similarity_search_with_score()`，把 `1-distance` 写入 `metadata["score"]` 供加权融合

**消融**：7 组配置，选定 `weighted_05_05`（向量/BM25 各 0.5 权重）

**指标变化**：

| 指标 | 基线 → +多路 | 变化 |
|---|---|---|
| Top1 | 74.73% → 71.43% | **-3.30pp** |
| Top3 | 92.31% → 93.41% | +1.10pp |
| Top5 | 94.51% → 97.80% | **+3.29pp** ← 最大收益 |
| 表格Top1 | 86.96% → 78.26% | **-8.70pp** ← 显著退步 |
| 表格Top5 | 95.65% → 100% | +4.35pp |

**归因（本报告最关键的判断）**：

BM25 的作用是**"扩池"而非"排序"**。Top5 +3.29pp 但 Top1 -3.30pp，说明 BM25 成功把原本掉出候选的正确文档捞了回来（Q13 计算机培养计划、Q57、Q83），但它的打分粒度太粗——只算词频重合，无法判断"哪一段才是真正回答问题的段落"，所以捞回来之后排在第 2~5 位，反而把向量路的 Top1 挤下去了。

**这个判断直接决定了后续路线**：既然问题在"排序精度"，那答案就是 Cross-encoder Rerank，而不是继续调 BM25 权重。事后验证：Rerank 加上去之后 Top1 从 71.43% 拉到 79.12%，超过了纯向量基线。

**表格子集退步机制**：表格 chunk 里可分词的中文 token 极少（大量是 `3.5 | 2 | 1` 这类裸数字和分隔符），BM25 打分接近 0；weighted 0.5/0.5 融合时，这一路的低质量分数**稀释了向量路的排序优势**，导致原本靠语义匹配排在第 1 的表格文档被拉低。

### 3.3 第 3 级：+Query 改写（结论：不启用）

**实现（三层架构）**：
- `src/query/rewriter.py`
  - 术语词典 29 条（"挂科"→"不及格课程"、"保研"→"推荐免试研究生"），**追加模式**而非替换
  - `CachedLLMRewriter`：LLM 多查询生成，MD5 key 本地 JSON 缓存，中断可恢复
  - `RewriteRetriever`：多查询 → 每变体走融合召回 → **加权二次 RRF**（原始 query 权重 2.0，LLM 变体 1.0）
- 严格 prompt：保留专有名词、禁止泛化、只生成 2 个变体、必须是疑问句
- 双模型对比：Qwen2.5-7B vs DeepSeek-V4-Flash（SiliconFlow）

**迭代了 4 轮**：

| 轮次 | 现象 | 根因定位 | 解决动作 | 结果 |
|---|---|---|---|---|
| 1 | 50 题全面退步 Top1 -4% | prompt 过松 + 词典重复追加 + 等权 RRF | 严格 prompt、去重、加权二次 RRF | 50 题表格 Top1 +6.6pp |
| 2 | 扩到 99 题又退步 -3.3% | Qwen2.5-7B 系统性幻觉 | 换 DeepSeek-V4-Flash | 幻觉消失，仍退步 |
| 3 | 换模型后仍退步 -4.4% | 根因变为**架构问题**：变体与原始 query 语义重叠 | 加 `llm_only` 对照 | llm_only 略好但仍不如 hybrid |
| 4 | 5 组消融确认 | 多查询扩展在 base retriever 已较优时净效果为负 | **决策：不启用，保留代码** | 止损 |

**为什么净效果为负（面试因果链）**：

多查询扩展的收益前提是"原始 query 检索质量差"。但本项目的 base hybrid retriever Top5 已达 97.80%——**正确文档基本都在候选池里了**，问题只剩排序。此时生成 2 个语义变体：
1. 变体与原始 query 语义重叠度 >90%，检索结果集高度雷同 → RRF 融合等于**给同一批文档重复投票**，排名几乎不变（85% 的题 unchanged）
2. 少数变体因 LLM 表述偏移引入噪声文档 → 在 RRF 里获得额外票数，**把正确文档挤出 Top1**（提升:退步 ≈ 1:2）
3. 即使把原始 query 权重加到 2.0，也只能减缓、无法消除稀释

**方法论价值**：这一级"失败"的实验，产出了本报告最有说服力的结论——**优化手段必须匹配瓶颈位置**。瓶颈在排序时做 query 扩展，是南辕北辙。

### 3.4 第 4 级：+Rerank

**实现**：
- `src/retrieval/reranker.py`
  - `SiliconFlowReranker`：调 `POST /rerank`，模型 `BAAI/bge-reranker-v2-m3`；`metadata` 原样透传 + 追加 `rerank_score`
  - **容错**：API 失败自动回退原始排序
  - `RerankRetriever`：包装 `HybridRetriever`，粗排 fetch_k=10 → 精排 top_k=5
- **关键设计决策**：Rerank 输入使用**原始 query**，不用改写变体——避免把阶段二的 LLM 噪声带进精排

**指标变化（hybrid → hybrid+rerank）**：

| 指标 | hybrid → hybrid+rerank | 变化 |
|---|---|---|
| Top1 | 71.43% → **79.12%** | **+7.69pp** |
| Top3 | 93.41% → 92.31% | -1.10pp |
| Top5 | 97.80% → 94.51% | -3.29pp |
| 表格Top1 | 78.26% → **91.30%** | **+13.04pp** ← 最大单点收益 |
| 表格Top3 | 95.65% → 95.65% | 持平 |

**Top3/Top5 微降的原因**：Rerank 出口从 top-10 收窄到 top-5，天花板本身降低；且 Reranker 存在模型偏好（把"勤工助学.docx"误排在"屏峰勤工助学岗位招募通知.pdf"之前）。生产环境优先保 Top1（用户最常只看首条），接受 Top5 小幅下降。

**为什么表格子集收益最大（+13.04pp）**：

Bi-encoder 把 query 和 chunk **独立**编码成向量再算余弦，表格 chunk 编码时语义信息本就稀薄（裸数字 + 表头碎片），向量落在语义空间的"模糊区"。Cross-encoder 把 `(query, chunk)` **拼接后一起过 Transformer**，每层 self-attention 都做 token 级交叉——即使 chunk 只有"3.5 | 2 | 1"，模型也能通过 query 里的"一等奖学金绩点要求"激活对"这是绩点门槛数值表"的判断。这正是 Bi-encoder 结构性做不到、而表格场景恰恰最需要的能力。

## 四、Badcase 深度分析（hybrid+rerank+dedup 后 Top-3 仍未命中 3 条）

去重后 Top-3 未命中从 7 条降至 3 条。剩余 3 条**全部不是召回算法能解决的**：

### 类型 A：时效性/范围缺失（2 条，占 67%）

| 题 | 期望文档 | 实际召回 |
|---|---|---|
| Q19 创新学分申请的时间范围 | `2025-2026...创新分申请补充说明.docx` | `创新学分认.docx/pdf` x3 |
| Q58 创新学分什么时候能申请 | 同上 | 同上 |

**根因**：`创新学分认定办法`（长效制度）与 `创新分申请补充说明`（本学期）**语义同族**，三路都无法判断"用户问的是本学期的具体时间范围"——这个信息不在文本里，在文档的时效属性里。

**这不是召回 bug，是 metadata 缺失**。解法：入库时抽取 `effective_date` / `doc_type`（制度 vs 通知）写入 metadata，检索时按"通知类优先、时间近优先"做业务规则加权。

### 类型 B：标注歧义（1 条）

| 题 | 期望 | 实际召回 |
|---|---|---|
| Q2 省政府奖学金申请条件 | `47号...奖学金评定及管理办法.pdf` | `名额分布.pdf` x2 + `附件2-省政府奖学金评选条件.docx` |

**根因**：`附件2-"省政府奖学金"特别优秀评选条件.docx` 从字面看**比期望文档更匹配**问题。属于黄金测试集标注质量问题。

### 去重直接修复的 4 条 case（关键收益归因）

| 题 | 无去重时 Top-3 | 去重后 Top-3 | 修复机制 |
|---|---|---|---|
| Q13 计算机专业毕业学分 | `软件工程/创新学分` x3 | `软件工程` + `创新学分` + **`计算机培养计划`** | 去重移除了"创新学分认定"的多余 chunk，为正确文档释放槽位 |
| Q38 勤工助学岗位如何报名 | `勤工助学.docx` x3 | `勤工助学.docx` x2 + **`屏峰招募通知`** | 去重把 `勤工助学.docx` 从 3 chunk 压到 2，空出 1 槽给正确文档 |
| Q65 勤工助学岗位谁可以申请 | `勤工助学.docx` x3 | 同上 | 同上 |
| Q99 计算机学院学生想申请勤工助学 | `勤工助学.docx` x3 | 同上 | 同上 |

**为什么去重后增量提升这么大（Top3 +4.39pp）**：

根因是 Rerank 后存在严重的**槽位浪费**问题。无去重时，Reranker 倾向于把同一文档的多个 chunk 排在相邻位置（因为它们的语义几乎相同，rerank score 高度接近）。典型表现：

- Q38/Q65/Q99：`勤工助学.docx` 一个文档占满 Top-3 全部 3 个槽位 → 5 个槽位实际只覆盖 1 份文档
- Q13：`创新学分认定` 占 2 个槽位 + `软件工程培养计划` 占 1 个 → 正确的 `计算机培养计划` 被挤出 Top-3

去重的作用是**强制多样性**：同一 source_file 最多保留 2 个 chunk，多出的槽位自动让给排名靠后的其他文档。这相当于在 Rerank 后加了一层隐式的 MMR（Maximal Marginal Relevance）——不需要计算 query-document 相似度，仅靠 source_file 维度就能实现有效的多样性控制。

**Top1 微降 -1.10pp 的原因**：Rerank API 非确定性波动（SiliconFlow API 每次调用返回的分数有微小差异），非去重本身引入。去重不影响 Top-1 位置（排名第 1 的 chunk 不会被去重移除）。

## 五、面试问答准备

### Q1：每级提升多少？

> 我在 99 条自建测试集（含 23 条表格类、8 条负样本）上做了五级链路消融，每级都用同一个评估入口跑，指标拆整体和表格子集两套。
>
> - **基线（纯向量 bge-large）**：Top1 74.7%、Top3 92.3%、Top5 94.5%
> - **+BM25 多路（weighted 0.5/0.5）**：Top3 +1.1pp、**Top5 +3.3pp**，但 Top1 -3.3pp、表格 Top1 -8.7pp
> - **+Query 改写**：Top1 -1.1pp、Top3 -1.1pp，**净效果为负，我把它下线了**
> - **+Rerank（bge-reranker-v2-m3，直接挂 hybrid）**：Top1 **+7.7pp vs hybrid**、表格 Top1 **+13.0pp**
> - **+文档级去重（同 source_file ≤ 2 chunk）**：Top3 **+4.4pp**、Top5 **+4.4pp**、表格 Top3 → **100%**
>
> 端到端：Top3 92.3% → **96.7%**（+4.4pp），表格 Top1 87.0% → **95.7%**（+8.7pp）。
>
> 数字之外更重要的是我通过消融搞清了**每级的作用边界**：BM25 负责"扩池"（Top5 +3.3pp 但 Top1 -3.3pp），Rerank 负责"精排"（Top1 +7.7pp vs hybrid），去重负责"释放槽位"（Top3 +4.4pp）。而改写在 base retriever Top5 已经 97.8% 的情况下，做的 5 组消融显示提升:退步 ≈ 1:2，所以我主动止损——**优化手段必须匹配瓶颈位置**。

### Q2：为什么 BM25 在教务这种"专名密集"场景收益大？

> 教务文档有一个显著特点：**同族文档密集，且区分它们的恰恰是低语义权重的专名 token**。
>
> 举真实例子：语料里有 4 份培养计划——计算机科学与技术、软件工程、网络工程、数字媒体技术。这 4 份文档 80% 的内容结构完全一样，Embedding 把它们映射到几乎重合的点上。用户问"计算机科学与技术专业毕业要修多少学分"，向量检索 Top-3 返回的是网络工程、软件工程、数字媒体——**语义上它没错，它确实都是"培养计划+学分"**。
>
> 但在词法空间里，"计算机科学与技术"这个 token 在 541 个 chunk 里只出现在极少数 chunk 中，**BM25 的 IDF 机制天然放大这类低频高判别力 token**。
>
> 同类场景还有：文号（`浙工大发〔2022〕46号` vs `47号`）、奖项名（"省政府奖学金" vs "优秀学生"）、制度类型（"补充说明" vs "认定办法"）、术语专名（"平均学分绩点"——我为此在 jieba 里预置了 13 个教务自定义词典）。
>
> 但 BM25 有**收益边界**：
> 1. **纯 BM25 Top1 只有 60%**——它单独不可用，只能作为第二路
> 2. **它扩池强、排序弱**：Top5 +3.3pp 但 Top1 -3.3pp，必须配 Rerank
> 3. **表格场景反而有害**：表格 chunk 可分词 token 极少，等权融合时稀释了向量路优势，表格 Top1 掉了 8.7pp

### Q3：表格子集为什么难？

> 表格难在**三个层次同时失效**：
>
> **① 切分层：结构被破坏**
> 表格被 chunk 切开后，表头和数据行分离。一个 chunk 里可能只剩 `3.5 | 2 | 1` 这样的裸数字矩阵，"这些数字是什么"的信息在**上一个 chunk** 里。
>
> **② 检索层：词面和语义双双失效**
> - **BM25 失效**：表格 chunk 可分词 token 极少，TF-IDF 打分接近 0。实测融合后表格 Top1 从 87.0% 掉到 78.3%
> - **Embedding 失效**：用户问"省政府奖学金有多少名额"，表格 chunk 里可能只有"项目名称 / 名额 / 备注"这样的表头，**"省政府奖学金"这个词根本不在 chunk 里**
>
> **③ 排序层：只有 Cross-encoder 能救**
> 加了 bge-reranker-v2-m3 之后，**表格 Top1 从 78.3% 涨到 91.3%（+13pp）**——是所有子集里收益最大的。
>
> 原因在架构：Bi-encoder 把 query 和 chunk **各自独立**编码成向量再算余弦。Cross-encoder 把 `(query, chunk)` **拼接后一起过 Transformer**，每一层 self-attention 都在做 token 级交叉——即使 chunk 只有裸数字，模型也能通过 query 里的"一等奖学金绩点要求"激活出"这是一张绩点门槛数值表"的判断。
>
> **但 Rerank 是补救，不是根治。** 真正的解法在切分阶段——表格整块保留 + **表头下沉到每个 chunk** + Markdown 化保留行列关系。

### Q4（可能被追问）：你的评估有什么局限？

> 我主动说三条：
>
> 1. **命中口径是文档级 `source_file` 匹配，不是 chunk 级**。只要命中任意一个 chunk 就算对——指标**偏乐观**。下一步要加 chunk 级评估
> 2. **8 条负样本只做了定性观察**，没有量化的拒答准确率。检索层对库外问题依然返回高分结果
> 3. **Rerank API 非确定性**：SiliconFlow API 每次调用返回的分数有微小差异，导致同一配置多次跑结果有 ±1pp 波动。理想做法是多次跑取平均，但 API 成本不允许
